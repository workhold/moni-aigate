# ADR-005：MVP 前采用单一现行架构，能力交付优先

日期：2026-11-04；状态：接受。依据：用户明确要求“MVP 交付之前，兼容问题都可以不用考虑太多”“不要有太多兼容代码，架构完整性，设计合理性，才是 MVP 的重点”。本决策覆盖此前计划中将历史兼容与完整证明候选置于业务功能之前的排期。

## 决策

- 新功能只围绕当前正式数据模型与明确的领域入口开发。MVP 前不承诺旧数据库、旧内部 API、未发布候选材料或竞品数据库的无损兼容；协议的公开支持范围仍须准确说明。
- 开发数据库可以按明确说明重建；必要数据演进优先一次性迁移或替换。不增加自动版本探测、双写、新旧双运行、失败 fallback 或无限期旧字段联合。
- 当前运行方式是 `serve` 启动服务，使用现行业务模块和正式数据库迁移。尚未接入服务的资金校验、历史重放、数据库环境识别和采购执行器实验暂时停止扩展，不作为业务功能的前置依赖。保留已有研究与验证记录，未完成部分不标记为完成。
- 不再为未发布的内部方案维护多套旧数据库结构、证明文件格式和执行路径，也不逐一验证它们与新方案的组合。替换时采用明确迁移或删除旧实现；这里不涉及取消已经声明支持的 OpenAI、Claude、Gemini 等外部 API 协议。
- 替换一个模块时，先明确现行模型、唯一写入口、事务所有权、故障状态和验收，再删除被替代的实现及调用；不同时保留两套“以防兼容”。本决策不要求为清理而立即删除所有离线研究与测试，也不将它们引入在线依赖。
- 当前服务的默认 Go 构建图不得包含只服务历史维护扫描的 raw reader、旧 scalar SQL 或维护装配。`internal/billing` 中这类 reader 与 `internal/maintenancescan` 采用 `historical` build tag，仅在显式历史专项命令中编译。它们不进入 `cmd/moni-aigate` 的 migrate、provision、serve、worker、wallet、billing、provider 或媒体依赖闭包。历史专项继续保留原测试和原数据库合同，不转换为当前服务能力。
- 继续保留租户隔离、数据库原子性、硬预占、唯一结算、不可变价格快照、未知消费不重发模型请求和秘密保护。简化历史兼容不等于省略现行业务正确性。

## 交付顺序

先做用户可见的纵向能力：经营报表与成本分析、客户与渠道运营、商品/套餐及选定支付接入，再收口单实例部署和实际供应商使用。需要真实服务或目标主机的部分单独记录条件；可以在本地独立完成的功能继续推进。媒体、长连接、HA 与完整历史认证按明确产品范围另排，性能优化在主要能力稳定后推进。

每片仍按 SDD：明确场景与非目标，冻结必要的数据/API/状态机，分工实现，再做与风险相称的专项验证并更新统一架构。避免为未发布版本穷举历史兼容测试。历史文档中的依赖树保留当时语境，当前优先级以本决策和[交付计划](../design/delivery-plan.md)开头为准。

## 当前影响

常规安装暂用已有正式迁移；不为绕过未完成候选门禁而直接安装候选 SQL。采购观察器按已完成范围交付后停止兼容扩展。下一片优先补齐请求时间窗口、模型及渠道维度的经营收入/采购成本与对账导出，直接服务对外 API 经营与渠道调配。
