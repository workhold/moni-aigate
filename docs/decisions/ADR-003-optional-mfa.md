# ADR-003：MFA 默认可选并保留扫码绑定

2026-10-30，ACCEPTED（开发者明确产品指示）。影响 NFR-02、T-02、AC-22；不改变资金、权限或双人审批合同。

## 决策来源

首版原设计要求平台管理员和财务账号先启用MFA。开发者在本机试用后明确要求：“这个能力可以默认不开启……最好是也支持二维码扫描……方便测试联调。”本次产品指示覆盖原先一律强制的基线，无需再次征求同一变更的批准。

## 行为

- 配置`MFA_ENFORCE_PLATFORM`缺省为false。未启用MFA的账号通过密码登录即可访问其角色授权的业务，控制台不将其强制跳转到绑定页。MFA不会自动启用。
- 配置true时，未绑定的平台管理员、财务制单员和财务审批员必须先绑定；普通客户账号仍可自行选择。`enrollment_required`由后端按当前策略和账号状态计算，前端只据此引导。
- 已主动启用MFA的账号在两种配置下均须完成动态码/一次性恢复码验证。关闭强制策略不删除用户密钥、恢复码、绑定状态或伪造已验证会话。
- 账号安全页支持浏览器本地二维码、手动密钥及otpauth URI。扫码是初次绑定方式；绑定后动态码由验证器应用生成，网页不代生成登录动态码。未启用阶段重新生成会使旧待绑定资料失效。
- 现有登录限速、CSRF、会话轮换、近期密码再认证、TOTP防重放、一次性恢复码、财务双人审批与审计均保留。可选且未绑定的账号再认证使用密码；已绑定时仍一并验证MFA。
- 丢失已启用因素不以切换此配置恢复，仍走受控身份恢复。该配置不提供已有MFA的关闭/重置接口。

## 实施与验收边界

应用配置和Identity会话状态共同落实策略，不能只隐藏前端警告。Compose与示例环境透传相同默认值；原有强制模式的测试需显式开启配置。新增回归应覆盖默认未绑定可进入业务、强制模式仍拦截、已启用时任何配置都不能跳过，以及配置切换后已有会话和个人绑定的行为。

现有验证记录保留原强制模式发生时的事实。此次变更的执行证据由独立增补记录承接，不能修改旧记录来宣称新配置已经验收。二维码合成解码与前端构建已有证据；真实用户绑定仍由用户自行操作。
