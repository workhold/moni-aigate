# 032：第二阶段文本数据面

2026-11-10；状态：实施合同已冻结（2026-11-14），见[实施冻结记录](implementation-freeze.md)；实现与验收按分片进行，尚未据此宣称完成。所属阶段：[第二阶段](../../docs/design/phase-roadmap.md#4-第二阶段bifrost-风格文本数据面)。前置：第一阶段 [029](../029-phase1-acceptance/spec.md) 全部通过。

Bifrost 是 Apache-2.0 的 Go 开源网关，固定参考提交见[海外研究](../../docs/research/ecosystem-overseas.md)。本规格只借鉴它已被源码证实的机制：失败分类先于回退、流首事件检查边界、以物理上游尝试为用量事实边界。它的 Enterprise 熔断文档、宣传性能数字和空占位文档都不作为实现依据。

## 1. 范围

只覆盖文本六协议。媒体、任务、Realtime 不参与（[路线 §2.1](../../docs/design/phase-roadmap.md#21-文本与媒体的当前结构)）。

本阶段不引入第二套路由、计量、结算、钱包或采购成本路径。所有能力都通过现有的 `Reserve → RecordAttempt → PrepareDispatch → Observe → Settle` 入口实现。

## 2. 测量基线

没有测量，就谈不上低延迟。先建立可信基线，再优化。

沿用 [002](../002-performance-parity/spec.md) 的 PERF-01..08，不改动其口径。本阶段补充三件事：

1. **压测使用 [031](../031-deterministic-mock-upstream/spec.md) 的 mock**，并用 `slow_ttfb`、`event_interval_ms` 固定上游行为。
2. **保留完整商业链路**。基础转发实验只能作诊断，不得标为完整产品性能。
3. **每次报告固定记录**：提交 SHA、构建参数、资源配额、数据库配额、mock 配置摘要、并发与活动流数、预热与采样时长、至少三次重复、原始逐请求样本。

首批目标沿用 002 §3 的工作阈值。未同条件实跑 Bifrost 与 Rust LiteLLM 之前，不宣称接近。历史 007 数据（本机 100 并发额外首字节 p95 为 61.56–69.74ms）只代表当时版本。

**验收**：在固定 4 vCPU / 8GB 应用与固定配额 PostgreSQL 上，完整商业链路产出一份符合 PERF-01..08 的报告。报告结论按实际结果写，可以是未达标。

## 3. 失败分类与故障切换

现有分类：`provider.FailureClass`（configuration、caller、network、upstream、rate_limit、credential、protocol、cancelled、timeout、model、quota、policy、rejected）与 `provider.Consumption`（unknown、not_sent、rejected_no_consumption）。`SafeToRetry` 只接受“可信无消费拒绝”或“未发送且网络类”。

### 3.1 本阶段不变的规则

- 重试资格只由 `Consumption` 决定，不由 `FailureClass` 或状态码决定。Bifrost 的可重试集合包含 500/502/503/504/529，那是可用性策略，不能推出上游未执行或未收费。
- 最多两次 attempt（跨渠道），不在同渠道换 Key。
- 下游已写出任何字节后不切换。
- 超时不是未消费证明；“没收到首字节”不足以证明安全。

### 3.2 本阶段新增

**健康作用域**。当前健康在内存，熔断窗口重启即重置。本阶段按失败类把健康动作落到明确作用域，并让需要持久的状态持久化。

| 失败类 | 作用域 | 动作 | 持久 |
|---|---|---|---|
| credential（401/403 且规范化为凭据失效） | credential | 隔离该凭据 | 是（现有撤销/隔离） |
| model（模型不存在、上下文超限） | binding / profile | 隔离该 binding | 是（现有 binding isolation） |
| rate_limit（速率） | channel + model | 冷却，遵守 Retry-After，上限由策略给出 | 否 |
| quota（额度耗尽） | credential 或 channel | 隔离，等待运营恢复 | 是 |
| network、upstream、timeout、protocol | channel + model | 熔断计数 | 否 |
| caller、cancelled、policy、configuration | 不计渠道故障 | 无 | — |

**熔断参数化**。把现在写死的“连续 3 次失败开 30 秒、半开一个令牌”改为路由策略版本里的受界参数：`failure_threshold`（2..20）、`open_ms`（1000..600000）、`half_open_tokens`（1..4）。仍在内存，重启后重置，这是已知限制。持久隔离只用于凭据、binding 与额度。

**流首事件检查边界**。参考 Bifrost 在返回成功前检查首个 chunk 内错误的做法：网关在向下游写出第一个字节之前，先读取并校验上游首个完整事件；首事件即为上游错误或协议错误时，仍可按 `Consumption` 判断是否换渠道。一旦写出首字节，就进入“已提交”，不再切换。首事件超时沿用现有 `PROVIDER_FIRST_EVENT_TIMEOUT`。

**不采用**：Bifrost 的“最后一个 attempt 不设首 token 截止时间”。moni 的每请求总 deadline 优先。

### 3.3 验收

用 031 的故障注入，在真实 PG 上断言：

- 每种故障对应的 `FailureClass`、`Consumption`、健康动作、是否换渠道、客户收费与采购成本；
- 对所有 `Consumption=unknown` 的故障，mock 接收记录中该请求恰好一条；
- 首事件错误在未写出下游字节时可换渠道，已写出则不换；
- 熔断参数按策略版本生效，策略变更只对新请求生效。

## 4. 预算治理

现有预算：Key 累计额度（017）、Key 运行限额 RPM/并发（016）、采购账户累计与周期预算（019、023-B）、客户钱包硬预占。

本阶段原则：**新增的任何预算只能是准入过滤或更严的限额，不能成为第二个余额。** 钱仍然只在钱包与 funding lot 中。

本阶段只补两项缺口：

1. **客户侧周期用量上限**（按 Key 或租户的日/月金额上限）。作为准入过滤实现：Reserve 事务内读取当前窗口已结算与持有金额，超限返回 402 `budget_exceeded`。它不保存余额，只读已有预占和结算。窗口边界使用 UTC，沿用 023-B 的窗口语义，不另造周期算法。
2. **预算命中的可见性**。拒绝原因、当前窗口已用与上限、窗口重置时间出现在客户控制台与请求详情。

分布式限流不在本阶段，随多实例设计。

**验收**：并发请求下不超过上限（含并发抢占）；预算拒绝不创建预占、不派发；窗口切换边界正确；重启后仍按数据库事实判断。

## 5. 缓存

缓存是本阶段最容易破坏商业不变量的能力，因此先定义语义，再实现。

### 5.1 语义决策

| 决策 | 内容 |
|---|---|
| 类型 | 只做**精确匹配**缓存。语义（embedding 相似）缓存不在本阶段：它需要额外 embedding 成本、跨租户泄漏风险更高、命中的正确性无法证明 |
| 作用域 | 租户内。缓存键包含 `tenant_id`、逻辑模型 ID、路由版本、规范化请求体的摘要。**不跨租户**，不跨路由版本 |
| 开关 | 按逻辑模型显式开启，默认关闭；开启时必须声明 TTL（60 秒–24 小时） |
| 适用请求 | 非流式 JSON 响应；流式暂不缓存。含工具调用的响应暂不缓存 |
| 存储 | PostgreSQL 表，保存响应正文与最终 usage 的规范量。不引入 Redis（HLD §5） |
| 隐私 | 响应正文是客户内容，沿用“默认不记录正文”的例外：仅当开关开启且仅存 TTL 内；到期删除；不进入日志、trace、报表 |

### 5.2 计费语义（待开发者决策）

缓存命中没有上游 attempt，但客户请求仍然发生。如何收费会影响账务路径，必须先决定，不能由实现者自行选择。

| 选项 | 客户收费 | 供应商成本 | 对现有路径的影响 |
|---|---|---|---|
| A（建议） | 与未命中同价：按缓存的最终 usage 和请求时冻结的售价结算 | 已知 0，无 attempt | 需要“无 attempt 但有可信最终量的结算”这一合同；现有无 attempt 路径只用于释放 |
| B | 命中折扣价 | 已知 0 | 需要新的价格维度，属于计价扩展，不在本阶段 |
| C | 命中免费 | 已知 0 | 客户可能通过重复请求套利，且报表收入含义改变 |

**决策点 D-032-1**：建议 A。选 A 的前提是在 028 合同中增加“cache-hit finalization”：一个 request、一份 reservation、一份 finalization、一份 settlement，没有 attempt，`supplier_usage_state` 为 known zero，来源标记为 `cache`。这是对现有链路的一个受控扩展，不是第二条路径。该合同冻结前不实现缓存。

### 5.3 验收（选定 D-032-1 后）

- 命中与未命中的客户账单一致（选项 A）；
- 命中请求有 request、reservation、finalization、settlement，无 attempt，供应商成本为已知 0；
- 跨租户、跨 Key 不共享（Key 级共享是否允许见决策点 D-032-2）；
- TTL 到期后不命中，且正文被删除；
- 命中请求不触碰上游（mock 接收记录无新增）。

**决策点 D-032-2**：同租户内是否允许不同 Key 共享缓存。建议：允许，因为 Key 授权已在命中前检查；但缓存键必须包含 Key 对该模型的授权检查已通过这一事实，不能绕过授权。

## 6. 插件与 Agent/MCP 边界

### 6.1 不可插件化

以下只能由核心模块实现，不开放任何扩展点：

- 路由选择与路由决策记录；
- 计量、报价快照、预占；
- 结算、退款、钱包与 journal 与 funding lot 写入；
- 采购成本记录与采购账户预算；
- 恢复与对账；
- 审计写入。

### 6.2 本阶段允许的扩展点（只读或不影响资金）

| 扩展点 | 限制 |
|---|---|
| 观测导出（OTel、日志） | 只读；使用现有白名单；失败不阻塞请求，也不得阻塞账本 |
| 请求准入前置过滤 | 只能**拒绝**，不能放宽任何限制；拒绝发生在 Reserve 之前或之内，不改变资金事实 |

插件执行环境（进程内脚本、WASM、外部进程）本阶段不做。如需要，另立 SDD，并先给出隔离、资源上限、失败语义。

### 6.3 Agent/MCP

不在前三阶段。网关不执行函数、不抓取 URL、不托管工具（LLD §3.1 现行规则）。若将来评估，必须先解决：工具调用的计量与计费、多轮会话的预占、工具结果的租户隔离、以及调用外部工具时的出口安全。这些没有合同之前不开放入口。
