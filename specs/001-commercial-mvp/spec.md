# 规格：001 商业 API 网关 MVP

状态：r3范围已获开发者同意并进入实施；r4对齐记录，2026-10-30；当前交付：v0.1.0-dev，正式发布验收未完成。

## 1. 已确认与待确认

已确认：moni-aigate 面向对外提供 API 的商业运营；参考上游设计后独立实现，不考虑 New API 二开底座；先审阅上游研究、HLD/LLD，再通过 SDD 开发。

本版基线：单实例；邀请制；CNY 预付费；人工核款审批入账；OpenAI-compatible 文本 Chat；24h 截止仍未结算则释放冻结，即使可信用量已保存；自动支付和多实例后置。2026-10-30开发者追加确认MFA默认可选，支持扫码绑定，替代先前平台/财务账号一律强制的基线；配置、已启用账号验证及边界见[ADR-003](../../docs/decisions/ADR-003-optional-mfa.md)。新增竞品清单用于补充设计研究，不扩大首版实现范围。

本版采用校准后的交付/收费矩阵：计费责任点前的无输出平台/上游失败免收、部分输出有可信最终量时收费、T2后网络失败保留收费等，依据开发者本轮继续实施的指示固定为本版契约。详见LLD §7.1。

SDD 流程：规格审阅 → HLD/LLD 与 ADR 固定 → 按纵向切片细化 API/SQL/fixture → 实现 → 以验收矩阵验证 → 更新设计与变更记录。规格变更必须说明受影响需求、任务和验收；不以“实现刚好如此”替代产品决策。

## 2. 用户场景

- 作为平台运营者，我希望接入一个可靠渠道，发布统一模型名称与售价，给客户授权，且无需泄漏上游凭据。
- 作为客户 owner，我希望核款入账后创建受限 Key，按公布价格调用并查询消费、冻结和退款。
- 作为财务操作员，我希望款项和原始业务号绑定，有不同账号复核，重复操作不会重复入账。
- 作为开发/运维，我希望用 request_id 解释请求被拒绝、如何路由、是否收费，并能在重启后处理未完成资金状态。

## 3. 功能需求

| ID | 规格（MUST 为首版门槛） |
|---|---|
| FR-01 | MUST 有真实租户隔离；身份上下文注入租户，客户无法访问其他租户资源；平台角色与客户角色分开。 |
| FR-02 | MUST 创建、一次性显示、限域、过期及撤销 API Key；Key 可配置 lifetime 花费上限，同租户不同 Key 共享钱包。 |
| FR-03 | MUST 提供获授权模型目录与文本 Chat（非流/SSE、客户端函数工具转发）；按版本化profile校验参数/输出上限/工具和计费维度；内部计量不受客户include_usage开关影响，不执行工具或隐式续写。 |
| FR-04 | MUST 支持同逻辑模型渠道池、优先级权重、并发健康过滤、最多一次安全重试及路由原因；未知是否消费不可透明重试；配置完整校验、不可变版本与原子发布，硬约束先于排序。 |
| FR-05 | MUST 有不可变售价版本、请求快照、微元整数结算；输入/输出定价与供应商成本分离，未知成本不等于零。 |
| FR-06 | MUST 以 PostgreSQL 保存 AVAILABLE/HELD 余额与不可变平衡流水；入账、冻结、消费、释放、退款事务化且幂等。 |
| FR-07 | MUST 在上游发送前持久预占；余额与 Key 上限不能被并发透支；收费≤预占且按固定收费政策裁决，重复结算不重扣，余款释放；估算/临时累计量不得当最终账单。 |
| FR-08 | MUST 有人工核款单与不同账号审批、业务号唯一；退款绑定原消费并累计封顶，追加补偿流水；钱包退款和现金退款区分。 |
| FR-09 | MUST 分离协议/传输/本地交付/usage可靠性/资金状态，持久终结证据后结算；按政策确定免收可直接释放，可能收费但最终量未知则限期待核对；重启不自动重发，24h截止仍未结算即释放且不追扣，已存可信量也不延长期限。 |
| FR-10 | MUST 提供客户钱包/Key/账单/请求页及平台渠道/价格/核对/审计页；request_id 关联，客户视图隐藏上游秘密。 |
| FR-11 | MUST 提供独立镜像与 Compose/部署脚本、健康探针、指标和备份恢复流程；明确单活动实例限制。1Panel 等面板部署仅为可选指南，不属于 MUST。 |
| FR-12 | MUST 分离计量事件/上游尝试/资金操作身份，保留来源与发生/接收时间；资金事务保存统计待投影事实，投影重放幂等且无资金副作用，更正关联原始事实；首版不开放外部计量摄取。 |

## 4. 非功能需求

| ID | 要求 |
|---|---|
| NFR-01 资金 | 同一pgx.Tx贯穿资金/Key/状态/审计/outbox，禁止helper另开写事务；真实PostgreSQL多连接/中断验证平衡、余额非负、唯一结算/入账、退款封顶与恢复。 |
| NFR-02 安全 | Key摘要、供应商凭据认证加密、会话/CSRF、登录限速、可选MFA（本地二维码/手动绑定）；`MFA_ENFORCE_PLATFORM=false`为缺省，true时强制平台/财务绑定，已启用者始终验证第二因子；敏感操作再认证与财务双人审批不变，SSRF防护，默认不存正文。 |
| NFR-03 可靠性 | 权威依赖/限流内部故障拒绝派发；全层统一attempt与总deadline，有界响应/流缓冲，取消后关闭并等待真实执行资源；不承诺上游exactly-once或单实例高可用。 |
| NFR-04 容量 | 在 HLD 固定基准条件下测量 100 并发流与代理额外首字节 p95；目标≤50ms，结果未测前不得写“已达到”。新增接近Rust LiteLLM/Bifrost的口径、有效内容计时与门禁见 [002性能规格](../002-performance-parity/spec.md)，不以关闭商业正确性换性能。 |
| NFR-05 可运维 | 恢复演练验证数据/密钥/订单一致性；RPO/RTO 目标需实际配置支持；上游成本有计量来源与待核对标记。 |
| NFR-06 来源 | 上游证据固定 SHA；禁止无授权拷贝业务代码/素材；复用路线变化必须更新 ADR、依赖与源码提供策略。 |
| NFR-07 观测 | 元数据/证据白名单与统一URL/错误脱敏；日志资源有界，非权威遥测故障不阻塞推理；资金、结算证据及成功敏感变更审计完整持久且不采样，拒绝类安全信号有界记录并计数；外部观测导出后置。 |

## 5. 明确不在首版

在线支付、自动现金原路退款、开放注册、代理商分销、多币种、套餐订阅、发票；原生 Gemini、图片/音频/视频/异步任务；语义路由、全正文审计、自动“内容合规”；多活动实例与 Kubernetes。Responses与原生Claude文本/基础工具已依据开发者继续到MVP的指令，按[003规格](../003-native-protocols/spec.md)前移；001原始资金/授权规则不变。其他能力须前移相应规格再实施。

2026-10-30开发者追加New API能力对齐要求，以上“首版不含”不代表永久不支持。后续范围与新增遗漏项已纳入[New API路线图](../../docs/design/new-api-roadmap.md)，按独立SDD切片实施；不能把路线图目标写成001已有功能。

## 6. 成功条件

一个客户从受邀开户、核款审批入账、创建 Key、发起非流/流式 Chat 到查询正确账单和必要退款，全链路可追踪；故障或重放不导致重复入账、透支或重复扣费；其他租户无法查看数据。完整 [验收矩阵](acceptance.md) 中 MUST 项通过，才能标记 v0.1 达到试运营出口。
