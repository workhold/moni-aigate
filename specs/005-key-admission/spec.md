# 005：按Key有界准入调度

2026-10-30，本地实现和回归完成；三对控制首byte降低、完成代价并存，见[实际记录](../../docs/verification/key-scheduling.md)，后续006继续处理完成阶段。承接002与现有热点证据：同Key的多个新请求在三个准入事务间争抢Key父锁，并占用PostgreSQL池等待。目标是在取得数据库连接前调度这些请求；收益必须通过同负载对照验证。

## 合同

1. 请求完成原有验证且取得global100/tenant32/key16运行许可后，按已认证内部Key ID加入FIFO准入队列。单Key至多16张票据（含当前持有者），空队列删除；只保存Key ID、交接状态，不保存凭据或正文。
2. 首次票据覆盖Reserve → RecordAttempt → PrepareDispatch → fresh Guard；在Plan.Start返回后、发上游之前立即释放。等待者不借用数据库连接、不持事务、不占渠道或半开许可。流执行仍按原渠道与运行许可生命周期处理。
3. 每次安全重试重新到队尾取票，只覆盖该次RecordAttempt/PrepareDispatch/Guard。不能合并重复请求、复用响应、提前扣除attempt额度或放宽未消费证据。
4. FIFO指登记的准入交接顺序，不保证供应商收到POST的顺序。不同Key独立；同租户钱包、结算与管理变更继续由数据库锁保护，不声称消除全部锁竞争。
5. 排队计入原请求总deadline及客户端TTFB/TTFC，不扣除排队耗时。取消必须移除等待票据或交还已授予票据，重复释放安全；函数退出或panic不泄漏票据。
6. 排队不缓存授权。获票后仍执行现有完整权限、资金、快照、持久派发及实例检查。预占前取消不产生资金事实；预占后取消沿用原释放/恢复，sending后崩溃不因本地队列推断未消费。
7. 平台probe保持现有全局/独立probe/渠道限制，不加入客户Key队列。客户排队者仍计入运行许可，不能移出许可计数美化容量。
8. 保留三段持久事务、所有锁强度、恢复/核对/审计/outbox与单实例约束。不增加生产测试绕过开关。若同源码控制没有稳定收益，则回滚生产调度并保留证据。
9. 关联审查发现原Plan.Start在admit回调panic时会遗留尚未转交的渠道/半开许可。本轮补全异常退出清理，保持panic传播与健康中性，不提前释放成功转交的实际执行许可。

边界：单活动实例内的局部调度，不代替数据库并发保护，也不是跨实例限流或通用任务队列。
