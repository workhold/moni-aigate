# 006：完成阶段共用Key调度

2026-10-30，本地实现、真实PG取消/超时恢复、全量race及轮换对照通过；50ms/目标资源与持续对标仍未通过，继承005和001资金合同。实际证据见[Key调度记录](../../docs/verification/key-scheduling.md)。

005的三对控制显示首字节p95降低14%–23%，但短突发全部完成变慢10%–15%。单次带观测的诊断仍发现完成阶段Key锁与连接池竞争，不能将该诊断时延当性能成绩。本切片让完成阶段也在借数据库连接前排队，验证能否保留首字节收益并降低完成代价。

1. 已持原runtime许可的客户请求，使用同一个按内部Key ID划分的有界FIFO调度器。一次请求同一时刻最多持/等一张票据；总数仍由global100/tenant32/key16约束。
2. `RecordFinalization → Settle`共持一次本地票据，仍是先持久证据、再独立结算的两个原有事务。只保存证据的失败尝试及之后独立Settle也分别取票，不改安全重试、恢复与收费矩阵。
3. 完成清理继续使用独立5s业务上下文；排队包含在该5s内，不因等待重置，底层事务仍按原有有界回滚退出。超时维持原billing_pending/持久恢复流程，不造usage、估扣、重放POST或强行成功。若时间全耗于队列、最终量尚未持久，RAM中的usage不能由worker重造，只能按原未知消费待核对/到期释放，不能承诺一定恢复为收费。
4. 票据在写客户响应/终态之前释放；不在读上游、写客户端或整条流期间持票。派发与完成公平交接，不给任何阶段无界优先级。
5. Key ID只用于本地调度分域，不作为新的授权或账本依据；实际财务调用仍按tenant/request读取不可变身份、取得全部原锁并检查证据。完成排队继续保留原渠道/运行许可，直到实际执行收尾，可能影响容量与尾延迟；不得为了成绩提前Finish。005中“等票无渠道许可”仅指新派发排队。队首Plan.Start遇渠道满仍立即失败，不持票等待渠道。人工财务、恢复worker、平台probe仍受原数据库保护，不宣称覆盖它们的所有竞争。
6. 所有事务、锁强度、可信证据先于结算、终态先收费、取消后清理与未知消费语义不变；交付观察仍仅记录本地写结果，不进入调度票据或改变结算。

性能裁决同时保留首字节、首有效内容和完成时间，不隐去005的完成回退。局部突发不代表持续吞吐或4vCPU/8GB认证。
